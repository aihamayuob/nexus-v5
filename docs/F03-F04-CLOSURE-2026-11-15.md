## 1. F-03 — planning-phase orphan mission never terminal — **VERIFIED (closed)**
- **Defect**: a mission whose process died while in `PLANNING` (before the plan checkpoint was saved) was skipped by `resumeInterruptedMissions()` forever: not resumable, not terminal, counted as active.
- **Fix** (`src/orchestrator/missionRunner.ts`, only in the "no `plan_definition` checkpoint" branch): a `PLANNING` mission is transitioned to `FAILED` with an explicit Arabic reason and its task row set to `failed`; idempotent. `RUNNING` without a checkpoint and `PAUSED` (Warden) are left exactly as before.
- **Test change, disclosed**: the old test "a mission with no persisted checkpoint is left alone" pinned the defect; it was replaced (with an explanatory comment) by two tests: F-03 orphan → FAILED (state, transition, task row, idempotent second pass, not resumable) and a scope guard (RUNNING stays RUNNING, PAUSED stays PAUSED). The "never COMPLETED" property is retained.
- **Evidence**: RED then GREEN; 4/4 mutants caught; real SIGKILL scenario S6(b) in `e2e/operational-scenarios.mjs` (39/39).

## 2. F-04 — task row keeps the requested provider after fallback — **VERIFIED (closed)**
- **Defect A (as reported)**: `claimTask` writes the *requested* provider/model before routing; after a fallback the row still named the failed provider.
- **Defect B (found while diagnosing, same root)**: in `chatService.ts` the fallback attempt was built with `model: providerModel || model`, i.e. the **primary's model string was re-sent to the fallback provider** (e.g. a `claude-…` name to OpenAI), contradicting the code's own comment. A real fallback to a real vendor would therefore have been rejected for an unknown model. `modelUsed` and the call-log `model` were wrong for the same reason. Not previously observable because every simulated server ignores the model name.
- **Fix** (smallest slice): `chatService.ts` — a fallback attempt uses `ProviderRegistry.resolve(p).resolvedModel`; `modelUsed` and the call-log record the model actually sent. `TaskRepo.recordServed(id, provider, model)` (no schema change; columns already existed). Called after a successful completion in the two legacy chat handlers (non-stream and stream) and in the v2 unified fast path. Failed tasks keep the requested provider (nothing served). Multi-node DAG/agent tasks are deliberately **not** touched (one task row, many completions — a single "served" value would be misleading).
- **Evidence**: `test/taskServingProvider.test.ts`, 7 tests on real HTTP servers; RED (5 of 7 failed for the right reason; the two scope guards passed), then 7/7. 6 mutants (fallback gets primary model; `modelUsed` = requested; each of the three `recordServed` call sites removed; provider-only update) — all caught, files restored byte-identical. Full backend suite 653/653.
- **Owner note (behaviour change)**: fallback calls now carry the fallback provider's configured model (`NEXUS_MODEL_<PROVIDER>` or registry default). An explicit client `model` applies to the requested provider only, as the code always intended. Real-vendor behaviour of this path is still UNVERIFIED (no keys).

## 4. Intermittent E2E check — tooling change **needs owner ratification**
- Known since CP-14 (E-1): `!payload.data.includes('42')` tests a random 152-char base64 string; "42" occurs by chance in ≈3.6 % of runs (re-measured: 3.59 % of 20,000 encryptions). CP-14 proposed a deterministic replacement and left it to an owner decision; this round it made `verify-all.sh` fail intermittently (run 1).
- **Change**: in `e2e/phase2-core-seed-flows.mjs` the predicate now decodes the ciphertext to bytes and requires that the UTF-8 bytes of the Arabic value and the key names `nested`/`emoji` do not appear (false-failure chance ≈ 2^-48). The old Arabic check was vacuous (a binary string never contains Arabic code points) — the new one is strictly stronger.
- **Evidence**: an identity "encryption" makes it fail (mutant), real AES-GCM 0/20,000 false failures, script 16/16 on 10 consecutive runs, in-script mutant → 15/16. The original script is preserved as `verification/seed-flows.mjs.before-2026-11-15`; reverting is one file copy. This is the fix CP-14 §E-1 itself proposed, but CP-14 reserved it for the owner, so it is reported rather than assumed.
