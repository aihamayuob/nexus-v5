## Context
ADR-006 lists MCP client, A2A and a connector SDK as "Not decided here". The 2026-11-15 owner-review report and the 2026-11-16 mandate ask for criteria to be written **before** code. This ADR records those criteria only.

## Primary-source check (2026-11-16)
Checked against `modelcontextprotocol.io/specification/versioning`: current revision is **2026-07-28**; each request carries `io.modelcontextprotocol/protocolVersion` in `_meta` (and `MCP-Protocol-Version` header on Streamable HTTP); `server/discover` exists; servers reply `UnsupportedProtocolVersionError` for unsupported versions; initialization-based revisions (<= 2025-11-25) are covered by a backward-compatibility section. **UNVERIFIED** (not read from primary sources yet): the exact tools/list, tools/call, `resultType` and auth details of 2026-07-28; the A2A v1.0 agent-card/`A2A-Version` details (taken from the R3 report only).

## Proposed criteria (M1.0 — gate before any M1 code)
1. **No new runtime dependency** (project has zero runtime deps). Hand-written, deliberately limited client; an official SDK may be used only in an out-of-repo interop test. Any exception needs a written technical justification.
2. **Tool-definition pinning**: on first approval store a hash of each remote tool's name + description + input schema; refuse (and audit) any later change until re-approved (defence against "rug-pull"/tool-poisoning).
3. **Egress safety (SSRF)**: allow only http(s); resolve DNS and reject loopback/link-local/private/metadata ranges unless the owner explicitly allow-lists the host; re-validate on **every redirect hop** (or disable redirects); no credentials forwarded across origins.
4. **Limits** (values to be confirmed by the owner; suggested): 30 s per call, 1 MiB response, 64 tools per server, bounded concurrent calls.
5. **Name separation**: remote tools are namespaced `mcp.<server>.<tool>` and can never shadow a built-in tool.
6. **Kill-switch + audit**: per-server disable flag that takes effect without restart; every connect/list/call/refusal is audit-logged without secrets.
7. **Privacy modes**: connection refused **before any network I/O** when the deployment is LOCAL_ONLY or the data class is PRIVATE.
8. **Effect classes**: remote tools default to `read_only`-equivalent gating; any effectful remote tool needs explicit per-tool owner approval.
9. **A2A inbound** only after F-06 is closed (F06-a done 2026-11-16; TLS via documented reverse proxy F06-b still PENDING), authenticated like every non-health route, no task execution without the existing pipeline.
10. **Acceptance tests first** (RED before code): pinning mismatch, redirect-to-private-IP, oversize response, name collision, kill-switch, LOCAL_ONLY refusal, no-secret-in-log.

## Not decided here
Whether to ship M1 at all before a first buyer demo; transport choice (Streamable HTTP only vs stdio); A2A scope; connector SDK shape.

## Implementation record — A1 A2A server (2026-11-18) — status: PARTIAL
Scope implemented: **A2A protocol v1.0, JSON-RPC binding, server role only**. Code: `src/a2a/a2aServer.ts` (Agent Card, `SendMessage`, `GetTask`, `CancelTask`), `src/routes/v2/a2a.ts` (`GET /.well-known/agent-card.json` unauthenticated and 404 when disabled; `POST /a2a` behind the normal gateway bearer auth), migration `019_a2a_tasks.sql` + `a2aTaskRepo` (task ownership). Opt-in: nothing is served unless `NEXUS_A2A_PROVIDER` names a configured provider (`NEXUS_A2A_PUBLIC_URL`, `NEXUS_A2A_WAIT_MS` 120000, `NEXUS_A2A_MAX_INPUT_CHARS` 20000 are the other knobs). An A2A task **is** a NEXUS task (same id, same `claimUnifiedTask`/`dispatchUnifiedTask`/`cancelTask` path, same pipeline/VEL/privacy gates); a peer can only read/cancel tasks its own gateway key created (other peers' ids answer "not found"). Idempotency key `a2a:<clientKey>:<messageId>` (cross-peer replays never collide).

Core fix found by this slice (E2E P8, observed FAILING before the fix): `chat`-kind tasks (the fast path used by `/v2/tasks`, `/api/chat` and A2A) interrupted by a crash stayed `running` forever after restart — a peer polling would never see a terminal state. Plans, missions, councils and VEL receipts already had boot recovery; chat tasks did not. Added `failInterruptedChatTasks()` (taskManager) + `TaskRepo.failInterruptedChat()`, run in `index.ts` **before** the server listens: pending/running chat tasks become terminal `failed` with an explicit reason. `runtime_plan` tasks are untouched (durable resume). Behaviour change to the core engine (affects `/v2/tasks` too): called out here for owner review. Tests `test/interruptedChatTasks.test.ts` (5; RED = missing export; 3 mutants killed).

Evidence: `test/a2aServer.test.ts` 14/14 (fake Anthropic SSE provider); `e2e/a2a-third-party-peer.mjs` — the **official `@a2a-js/sdk` 1.3.0 client** against the BUILT backend as a separate process: card discovery, SendMessage→COMPLETED with artifact, GetTask, returnImmediately, CancelTask while another task completes, no-credential client rejected with zero provider traffic, SIGKILL + restart on the same DB (completed task intact; in-flight task resolves to FAILED; new task completes) — 9/9. Full backend suite 749/749, typecheck clean. Acceptance mapping: A-A1.1 spec-conformant card — VERIFIED against the official SDK parser only; A-A1.2 real peer interop — VERIFIED for one vendor SDK/one version; A-A1.3 unauthenticated peer rejected — VERIFIED; A-A1.4 restart recovery — VERIFIED for the paths above (in-flight chat tasks are FAILED, not resumed).

Limits (not claimed): streaming (`SendStreamingMessage`/`SubscribeToTask`), push notifications, `ListTasks`, extended Agent Card, gRPC/HTTP+JSON bindings, Agent Card signing, multi-turn (`contextId`/`taskId` continuation), message history and non-text parts are NOT implemented (answered with the spec's "unsupported" error). Tasks run on the single operator-configured provider; there is **no per-peer privacy mode** (if that provider is a cloud one, peer input goes to the cloud) — owner must choose a local provider for sensitive deployments. A peer cannot approve an `INPUT_REQUIRED` (approval-gated) task. The artifact is rebuilt from stored events, so it is subject to event retention pruning. The spec was read only partially (parts of the document were truncated when fetched). No other vendor's A2A client was tested; no TLS/public-internet operation was exercised (loopback only; TLS is via the documented reverse proxy).
